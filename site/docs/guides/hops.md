# What a hop does [#](https://booster.apps.wayne.edu/docs/guides/hops.html#what-a-hop-does)

This page walks through one hop step by step. The full list of hops is in [the reference](https://booster.apps.wayne.edu/docs/reference/hops.html).

On PHP hops a pre-pass runs first: PHP 4 era `$a = &new Foo();` becomes a plain assignment, because PHP 7 and newer refuse to compile the old spelling and Rector would never get a parse tree. The report lists the rewrites per file under `Pre-pass fixes:`.

1. Rector runs as a dry run. If it reports errors, the run stops before anything is written. So does a hop that would change more than 200 files, unless an interactive run confirms it after showing the per-rule summary; an explicit `--max-changes` is a hard limit that never asks. An empty Rector report usually means the process ran out of memory, and the message points at `--memory-limit`.
2. Rector runs for real, with only that hop's rules. A rule that would change what the code does is never applied: the PHP 8.0 set's switch-to-match rewrite is skipped, because `match` compares strictly and would stop a `case 1:` from matching the string `"1"` a query string carries. Every run keeps Rector's and PHPStan's caches in its own temp directory, removed at exit, so one run never reads another's.
3. `composer.json` is edited: the `php` or `laravel/framework` constraint is raised, and `config.platform.php` moves with it when the app already pins it, to the first released patch of the new PHP (8.4.1 for 8.4, because 8.4.0 never shipped; x.y.0 otherwise). Booster never creates that key.
4. The gate runs the app's tests inside `booster-target:<php>-<stamp>`, a container built from `docker/Dockerfile` on the PHP the hop moves to. The stamp is a short hash of the recipe, so an edited `docker/Dockerfile` rebuilds the image instead of reusing a stale one. The image carries the extension set Citadel's apps run with: intl, ldap, soap, zip, gd, pdo_mysql, mysqli, bcmath, pcntl, exif, redis, imagick and oci8. The first build downloads Oracle Instant Client for oci8, so it takes a few minutes; later hops reuse the image. Pass `--image` to run the gate in your own image instead (below). A red gate stops the run and leaves the changes in place so you can read them (`git checkout .` undoes them). With `--replay`, the gate also replays the requests recorded before the first hop and fails on a changed answer: see [The replay gate](https://booster.apps.wayne.edu/docs/guides/replay-gate.html). To check the image itself, `scripts/check-target-image.sh` (or its Windows twin `check-target-image.ps1`, PowerShell 7.3 or later) builds it for each PHP version and verifies its extension list, that Composer runs and, on the archived Debian releases, that apt can verify the archive; it needs Docker and a few minutes per version, so it is not part of `composer ci` (a unit test reads the recipe instead).
5. On Laravel and PHPUnit hops the gate refreshes the lock before the tests: `composer update -W` for the package the hop moved, so `composer.lock` lands on the new major version next to `composer.json`. A PHP hop reads the lock first: a locked package whose own `require.php` leaves out the hop's PHP makes a plain `composer install` refuse the whole lock, so the gate runs `composer update -W` for just those packages, inside `composer.json`'s constraints, and the report names each one (`the lock held symfony/service-contracts v1.1.2, which needs php ^7.1.3, not PHP 8.0`). The lock follows the app up one PHP at a time, and each hop's diff moves only what had to move. Otherwise, a PHP hop on an app with a `composer.lock` runs `composer update --lock`: no package moves, but the lock's content hash catches up with the raised `php` constraint, so no hop leaves "The lock file is not up to date" behind, and on an app that pins `config.platform.php` (every Sourdough app does) the lock's `platform-overrides` catch up with the new pin, which a plain `composer install` would otherwise check the raised `php` constraint against and refuse. Every other hop, and the baseline, run a plain `composer install`. The two phases report separately: a Composer failure names the Composer phase and Composer's own output, because the tests never ran.

When the run raised the app's PHP floor, its report ends with a list of the other places that still name an older PHP, each with its file and line: PHP versions in the CI matrix (Preflight's `php_versions`, a GitHub workflow's `php:` matrix, a `PHP_VERSIONS` list) and PHP images (`php:8.3-cli` in a CI job, `citadel/php-apache:8.4r5` in the Squire kit's `.env.squire.example` or `docker-compose.squire.yml`, the `image` in Parity's `parity.json`, a `FROM` line in the app's own `Dockerfile`, an `image:` in its `docker-compose.yml` or `compose.yaml`), and Laravel Sail's runtime (`vendor/laravel/sail/runtimes/8.3` and `sail-8.3/app` in a Sail app's `docker-compose.yml`). Booster never edits CI or deploy files, so it lists them instead: a matrix entry below the floor fails on the first push, because Composer refuses to install below it, and an image below it can no longer run the app. A Citadel tag also carries a build revision (`8.5r3`) that Booster cannot know; for `parity.json`, `parity image list` shows the Citadel images Parity can run. A dry run lists them too, from the floor its last PHP step would set. The JSON report carries them as `floor_follow_ups`.

Composer 2.10 refuses to load tagged releases Packagist has flagged with a security advisory, and hops that move onto Laravel 9 or 10 most often meet that block. The refusal has two faces. The loud one fails the install phase and names the advisories. The quiet one happens when the app allows dev stability: Composer does not fail at all, it locks the branch instead, `9.x-dev` where the hop asks for `^9.0`. Booster reads the refreshed lock back and treats a branch version behind a tagged range like the block. Either way it writes a temporary entry to `config.policy.advisories.ignore` in `composer.json`: scoped to the package and the constraint Composer refused, kept visible to `composer audit`, and carrying a reason PROCTOR can find and report until the app removes it. The gate then retries once. If the retry still fails, the run stops with the unblock and the failure both in the report, and the entry stays in `composer.json`.

The unblock is temporary by name, and Booster enforces that. When a gated step passes, Booster re-reads `config.policy.advisories.ignore` and reports every entry whose reason carries its own prefix (`Booster temporary unblock`; older runs wrote `BOOSTER temporary unblock`, which it still recognizes). A step that is not the plan's last one applies with a warning; the plan's last step fails until the entry is out of `composer.json`, so the final target never ships with the unblock still in place. Removing the entry is the app's job once it is off the blocked versions.

The `--image` value names the image the baseline and every gate run in, and it takes three shapes:

- One name, used for the baseline and every gate: `--image myapp/gate:8.4`.
- A template whose `{php}` is replaced with the PHP version of that baseline or gate: `--image registry/php-apache:{php}` gates the 8.1 hop on `registry/php-apache:8.1` and the 8.2 hop on `registry/php-apache:8.2`.
- A map of PHP version to image, for a fleet whose images do not follow one pattern: `--image 8.0=legacy/php:7.4,8.1=registry/php-apache:8.1`. A map without the version a baseline or hop lands on stops the run before the first hop and names the fix; a template never misses.

Booster never builds a `--image` image: it must exist locally or be pullable, and each resolved image is pulled at most once per run. On an arm64 Mac, Citadel's published images such as `citadel/php-apache:8.5r3` are amd64 only: pass an arm64 build via `--image`, or set `DOCKER_DEFAULT_PLATFORM=linux/amd64` and let Docker emulate. `booster-target` itself builds natively on arm64 for PHP 5.6 and up; the official `php:5.5-cli` image is amd64 only, so a PHP 5.5 gate on arm64 runs under Docker's emulation (slow) or needs an amd64 machine. And the old-PHP images (5.5 through 8.0) point apt at archive.debian.org, so they get no security updates: they exist to run the app's tests on the way up, not to serve traffic. apt still checks the archive's signatures there, against Debian's current archive keys, which the recipe copies in from pinned Debian images because the keys those old images ship with have expired. Jessie (PHP 5.5) is the one exception: its archive is signed only by expired keys, so its image installs packages unsigned while it builds, and that setting is removed before the image is done.

`run` refuses to start on a working copy that is not under git or has uncommitted changes, so the upgrade diff stands alone. `--dry-run` has no such limit.

A dry run previews every hop against the original tree, so the same file can appear in several hops. The report ends with the number of unique files and a reminder that nothing was applied. A Laravel hop whose app has no `vendor/` cannot see the framework's classes, so its preview is marked incomplete and the report says to run `composer install` first.

A run prints one line per hop to standard error while it works: the hop's position in the plan, its id, its status, the number of files it changed and the seconds it took, and a final line totals the hops run, the stops and the whole run, baseline included. The baseline gets a line as it starts and one as it ends, since its first run on a machine builds the gate image and can take minutes before the first hop line. They go to standard error so the report on standard output is untouched and `--format json` stays valid JSON.

`node-pin-24` floors Node at the Node the app deploys on, not just the newest one. A floor above the server's Node makes every `npm ci` there warn (`EBADENGINE`), and the hop's gate never builds on the server's Node either. So the major comes from, in order: `--node=<major>` (22, 24 or 26 today; the policy must still support it); the Node the app's Citadel image ships, which the Squire kit mirrors as `NODE_IMAGE` in `.squire/base-fallback.Dockerfile`; and otherwise the hop data's target, the newest Node the policy supports (26 today). The plan's step line says `node-pin-24 (pins Node 22)`, and its summary says where the 22 came from. `--node` also puts the Node hops back in a plan that passed a target version, as `--with-node` does. The later front-end hops run in the same `node:<major>` container. A Node floor is like a shelf: put it higher than the server can reach and nothing lands on it.

Four hops edit manifests instead of code. `node-pin-24` sets `engines.node` in `package.json` and writes `.nvmrc`, then proves the front end still builds on the pinned Node: when `package.json` has a `build` script and a `package-lock.json`, it runs `npm ci` and `npm run build` in the `node:<major>` container before the app's usual gate, and a red build stops the run there. With no build script it says so plainly and runs the usual gate. `mix-to-vite` converts a simple `webpack.mix.js` to Vite (see [the hop list](https://booster.apps.wayne.edu/docs/reference/hops.html)) and asks for a build gate, which runs `npm ci` and `npm run build` in the `node:<major>` container (the plan's Node pin, 26 by default) before the app's tests. `vite-major` moves a Vite front end onto the Vite major in the hop data: it pins `vite` wherever it sits in `package.json`, pins `laravel-vite-plugin` and `@vitejs/plugin-vue` to the hop data's versions when they are already listed, runs `npm install` in the Node container and asks for a build gate. `tailwind-3-to-4` runs the official `@tailwindcss/upgrade` tool (one exact release, with `--force`) in the Node container, then pins `tailwindcss` to `^4.1`, adds the matching Vite or PostCSS plugin, removes `autoprefixer` and `postcss-import`, which Tailwind 4 folds in, moves an inline `css.postcss` Tailwind block in `vite.config` to the `@tailwindcss/vite` plugin (the early 2025 Laravel starter kit shape; any other config that still imports them gets a MANUAL line), and runs `npm install` so the lock matches; plugins listed in `tailwind.config.js` and `@apply` inside Vue SFC `<style>` blocks stay manual work, and the hop says so. `inertia-2-to-3` raises `inertiajs/inertia-laravel` and `@inertiajs/vue3` to `^3.0` when the plan lands on Laravel 11 or newer on PHP 8.2 or newer, runs `composer update` and `npm install`, and lists the v3 breaking changes as manual lines, because a person works them. `typescript-major` pins `typescript` to `^6.0` wherever it sits in `package.json`, and `vue-tsc` to `^3.0` when the app lists it, runs `npm install` so the lock matches, then asks for the same build gate; when that install has to override a peer dependency, the hop names the package to raise, because the next plain `npm install` would refuse the tree; running the type check and fixing what the new major flags stay manual work, and the hop says so.

Vue 2 to Vue 3 is staged. `vue-26-to-27` moves the front end to the last Vue 2 release, which carries the Vue 3 reactivity API; `vue-27-to-compat` switches to the `@vue/compat` build; `vue-compat-codemod` runs the `vue-upgrade-tool` codemod and keeps every manual item it lists. `vue-2-to-3` is the playbook that stands in for all three: skipping it skips them, and a person finishes the job, because Rector does not read Vue.
